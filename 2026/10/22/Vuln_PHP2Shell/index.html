Security | PHP2Shell：内存耗尽之后，服务器怎么就被拿下了？

免责声明

本文由 LLM 参与创作。内容仅供学习研究与授权环境中的安全分析，请勿对未授权系统开展测试。文中利用机制均来自已公开的安全研究与官方通告，代码片段为简化示意。

0x00 引言：一行 echo 的页面，为什么能被打穿？

<?php
echo "OK\n";

2026 年 10 月 21 日，PHP 紧急发布 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35，修复两个 CVSS 4.0 均为 9.2 的未认证远程代码执行漏洞：CVE-2026-109618（OOM corruption）和 CVE-2026-109619（stale global state）。社区将这组漏洞称为 PHP2Shell。

上面这个页面没有数据库、没有上传、没调 session_start()，但在公开的利用实现里，它就是标准的攻击目标——纯 HTTP 打进去，拿到 uid=33(www-data) 的命令执行。

秘密全在 echo 的前后：PHP 处理一个请求，要先解析输入、初始化运行环境，结束后还要做请求清理。业务代码只占中间一小段，而这两个 CVE 恰好埋在准备和收尾的工作里。内存耗尽（OOM）这个最普通的故障，在特定时序下会变成攻击者的遥控中断源——这就是整条利用链的起点。

先补一点背景：上传一个文件，PHP 到底做了什么？

平时上传头像、提交附件，页面上看起来只有“选择文件”和“提交”两个动作。服务器实际要先拆开整个请求，分清哪些是普通文字、哪些是文件，再为业务代码准备数据。PHP2Shell 涉及的几个关键环节，就藏在这段准备工作和之后的清理工作里。

第一步：浏览器把表单编码成 multipart。 一个普通的上传表单大致如下。这只是正常上传功能的示例：

<form action="upload.php" method="post" enctype="multipart/form-data">
  <input type="text" name="description" value="旅行照片">
  <input type="file" name="photo">
  <button type="submit">上传</button>
</form>

multipart/form-data 可以理解为“一个包裹里装了多个小包”。浏览器用 boundary 分隔各个 part；每个 part 的头部说明字段名，文件 part 还带文件名等信息，后面接实际内容。上面的请求包含两部分：description 的文字，以及 photo 的文件数据。这里的 part 指请求体中的一个分段，和一次新的 HTTP 请求是两回事。

第二步：Web 服务器把请求交给 PHP。 常见部署有两种：Apache 的 mod_php 把 PHP 嵌在 Apache 进程内运行；PHP-FPM 则维护独立的 PHP 工作进程，由 Nginx 或 Apache 通过 FastCGI 把请求交过去。后文出现的 SAPI，就是 PHP 与外部运行环境衔接的接口；worker 则是实际处理请求的工作进程。一个 worker 通常会陆续处理多个请求。

Web 服务器还可能先缓冲请求体，再交给 PHP。因此“浏览器正在上传”和“PHP 正在解析上传数据”这两个时间段，具体如何重叠取决于部署配置。

第三步：PHP 解析请求，建立业务代码能直接读取的数据。 在开启自动 POST 解析的常见配置下，PHP 会在执行目标脚本之前处理适用的 POST 请求体。multipart 解析器逐段读取输入：普通字段进入 $_POST；文件内容通常写入上传临时文件；文件的名称、大小、临时路径和上传状态则记录到 $_FILES。

浏览器提交 multipart 请求
  └─ Web 服务器交给 PHP
      └─ PHP 解析请求体
          ├─ 普通字段 → $_POST['description']
          ├─ 文件内容 → 服务器上的上传临时文件
          └─ 文件信息 → $_FILES['photo']
      └─ 执行 upload.php
          └─ 业务校验后，再决定是否保存文件
      └─ 请求收尾：清理本次请求的数据和剩余临时文件

$_POST、$_FILES 属于 PHP 的“超全局变量”，脚本可以直接读取。以上面这个表单为例，$_FILES['photo'] 里的关键字段包括：

  • name：客户端提供的原始文件名。
  • tmp_name：服务器保存上传内容的临时路径。
  • size、error：文件大小和上传结果。
  • type：客户端提供的 MIME 类型，业务端仍需验证实际内容。
  • full_path：客户端提交的路径信息，PHP 8.1 起提供，同样需要按不可信输入处理。

此时文件还只是被临时接收。业务代码接下来检查身份权限、错误码、大小和实际文件类型，再用 move_uploaded_file() 等操作保存到选定位置。正常请求结束时，未移走的上传临时文件会被清理。接收与解析发生在前，应用决定接受或拒绝发生在后。 具体字段与处理流程可以对照 PHP 官方文件上传手册。

文件放在临时目录，为什么还会牵涉内存？

文件内容写入临时文件，PHP 仍要在内存里维护解析缓冲、字段名、字段值，以及描述文件的数组。$_FILES 保存的是文件信息，文件正文通常留在临时文件中。

PHP 数组在内核里主要由 HashTable（哈希表） 实现；其中的元素槽位叫 Bucket，值使用 zval 表示。可以先把它们理解为“目录”“目录中的一条记录”和“这条记录保存的值”。每条记录除了用户提交的文字，还带类型、长度、引用等管理信息。因此，请求体大小、文件大小和 PHP 分配的内存大小，是三个不同的量。

几个常见配置也分别负责不同环节：upload_max_filesize 管单个上传文件，post_max_size 管 POST 请求体大小，memory_limit 管 PHP 分配器允许使用的内存。后面提到 OOM（Out Of Memory），指内存分配无法按原有方式继续的情形；触及 PHP 的内存限制时，整台服务器仍可能有空闲内存。

上传进度条，为什么又和 session 有关系？

上传大文件时，页面需要知道“已经处理了多少字节”。PHP 的 Session Upload Progress 功能可以在解析上传数据的过程中，把进度写入 session，让另一个查询请求读取。

session 可以理解为服务器保存的一份会话数据，浏览器通常通过 cookie 中的会话标识找到它。除了登录状态，它也可以存放上传进度等临时信息。当上传进度功能开启、请求携带相应标记并满足处理条件时，PHP 会在上传解析阶段更新这些数据。

这里最值得记住的是 官方手册的提醒：上传进度信息在任何脚本执行之前就会写入 session。 所以，目标脚本是否显式写了 session_start()，和 PHP 内核是否已经接触 session 状态，要分开看。

这也回答了开头那个问题：即使页面只写了一行 echo，只要请求被交给 PHP 且相应解析功能启用，PHP 仍会先完成自己的准备工作。页面上有没有上传按钮，由前端决定；服务端解析哪种请求，由实际收到的请求和运行配置决定。

请求结束了，worker 为什么还在？

为了减少启动开销，worker 通常会复用；但本次请求分配的大量内存会在请求收尾时释放。于是出现了两种不同的寿命：工作进程可以跨请求存活，请求内存只服务于当前请求。

如果进程里的某个字段仍保存着已经释放的内存地址，它就成了“悬空指针”；后续通过它访问原对象，就是 UAF（Use After Free，释放后使用）。后文的 RINIT 和 RSHUTDOWN，分别指扩展的请求初始化与请求结束处理；析构则是销毁一个值并释放其资源时执行的收尾操作。

对象释放后，旧引用仍需撤销；访问前也要确认对象有效。

PHP 对许多可共享的数据使用引用计数管理寿命，可以理解为“还有多少处在使用它”。释放一个值时，计数会减少；最后一个使用者退出后，底层数据才具备回收条件。这个机制依赖记录正确：如果代码把无效内存误认成正常的值，清理操作也会跟着读错记录。

后面还有两个容易混淆的词：序列化是把数组、对象等数据转换成便于保存或传输的表示，反序列化是把它们还原回来。还原复杂数据时，PHP 会维护一个工作上下文，记录已经处理过的值、引用关系和待清理对象；上下文也有自己的初始化与销毁过程。理解这一点，就能看懂后文为何同时讨论业务数据和“负责还原数据的内部状态”。

带着这几组关系再看源码，就容易抓住重点了：上传解析会建立数据结构，进度记录会提前接触 session，异常退出会改变清理顺序，而 worker 复用让部分错误状态有机会延续到后续请求。

0x01 漏洞披露：一条二十年长的伏笔

PHP2Shell 的时间线本身就是个好故事：

  • 2004：Stefan Esser 发现 PHP 首个 memory-limit 远程漏洞，exploit 从未公开；
  • 2020：bug #78876 报告 multipart 长变量导致 OOM 与临时文件残留，当时没深究；
  • 2024：OSTIF / Quarkslab 审计 PHP 时重新发现相关问题，利用未证明，未修复；
  • 2026-08：安全研究方 Calif 在 OpenAI “Patch the Planet” 项目里重新审视这段历史，几天内找到第一个 OOM-fatal 中断点，随后扩展出针对 mod_php 和 PHP-FPM 的可靠利用；8 月 11 日报告 PHP，8 月 15 日 PHP 官方确认 RCE PoC 有效；
  • 2026-10-21：补丁发布，同步披露 GHSA-w8hw-w9fx-j79w 与 GHSA-6wmf-4rv5-p3rp。

官方确认的利用范围：mod_php 在默认输入与内存限制、正常 prefork 多 worker 下，已在业务代码运行前验证完整 RCE，实测目标覆盖 WordPress、Drupal、Joomla、Magento、phpMyAdmin、Nextcloud、Laravel 等；FPM 侧也有官方验证的 session 生命周期 RCE，前提是应用存在可达的解码操作。Calif 将已发现路径最早追溯到 PHP 5.4，修复覆盖 8.2–8.5，另放出 7.4 / 8.0 / 8.1 的最小源码回补分支。

一手研究见 Calif 的 PHP2Shell 研究。

0x02 先看 patch：PHP 怎么改掉”OOM 即跳转”

8.4 分支的修复提交是 506e87fa（8.5 为 31c0ea7d），提交说明只有两行：

Avoid state corruption via bailout

- Replace bailout on OOM with UnwindExit
- Properly reset various globals that may be accessed during startup

完整 diff 的核验结果为：402 个文件、+11112 / −1032 行，横跨 Zend、session、序列化、几乎全部扩展和 OPcache。改动密度本身就说明问题：这是一类生命周期缺陷，散布在所有”发布状态 → 干可能失败的活 → 提交”的代码路径上。

软 OOM：从”立刻跳走”改成”先记账，到安全点再退”

旧 Zend MM 触发 memory_limit 时走 zend_error_noreturn() → zend_bailout()，一次 longjmp 直接跳出当前执行流。如果此刻某段 C 代码正把内部结构改到一半，跳出去就再没人替它收尾。

这里的 Zend MM 是 PHP 内核的内存管理器。平常调用函数，会沿调用关系逐层返回；longjmp 则直接回到事先保存的执行位置，沿途尚未执行的语句会被跳过。可以把它理解为“紧急撤离”：人已经离开，手头改到一半的记录还留在原地。PHP 的 bailout 就借助这种机制中止当前处理。

补丁引入了延迟 OOM 状态机：

typedef enum _zend_oom_state {
    ZEND_OOM_STATE_NONE = 0,
    ZEND_OOM_STATE_PENDING,
    ZEND_OOM_STATE_HANDLING,
    ZEND_OOM_STATE_HANDLED
} zend_oom_state;

触及软限时先记下错误信息并置 VM 中断标志，等执行器跑到安全检查点再统一处理：

EG(delayed_oom).filename = script_filename;
EG(delayed_oom).lineno   = script_lineno;
EG(delayed_oom).state    = ZEND_OOM_STATE_PENDING;
zend_atomic_bool_store_ex(&EG(vm_interrupt), true);

VM 是负责执行 PHP 指令的虚拟机；执行帧记录当前函数执行到哪条指令、有哪些参数和局部变量。补丁在有执行帧时使用 zend_throw_unwind_exit()，让执行器沿受控的退出路径展开；没有执行帧时，处理器仍会在检查点调用 zend_bailout()。这里的“安全点”指显式检查并处理延迟 OOM 的位置，将退出集中在这些位置，可以减少在底层结构更新中途直接跳走的问题。配套还新增了 femalloc 族可失败分配接口——分配失败返回 NULL，调用方显式处理半成品，替代旧的”失败即跳转”假设。

硬 OOM：放弃常规收尾，直接终止进程

延迟处理也要有底线。内存继续恶化时，zend_mm_check_limit() 走 zend_mm_hard_limit_error()，向 stderr 报告后 _exit(137) 直接退出进程，跳过所有依赖内部状态的请求清理。硬限按分段公式计算（软限 ≤ 1 GiB 时取 2 倍，超过则加 1 GiB，均可显式配置百分比），别把”两倍”当成固定规律。

两个易读错的点：修复后软 OOM 仍会打印 Allowed memory size ... exhausted，这句报错与补丁有无无关；_exit(137) 是主动带状态退出，和内核 SIGKILL 是两回事。

跨请求状态：把”遗留”变成”不可能”

第二类修复针对 109619：请求结束后，进程级结构里指向请求内存的字段必须清空。

读这些代码时，要区分“保存地址的字段”和“地址指向的数据”。字段所在的结构可以跟随 worker 长期存在，数据却可能只属于当前请求。类似通讯录里还留着旧地址，原住户已经搬走，下一位使用者照着地址寻找，就会认错对象。这里说的内核 globals，也有别于业务脚本里一个普通的全局变量。补丁在 php_request_shutdown() 里对 superglobals 析构后立即置 UNDEF：

for (i = 0; i < NUM_TRACK_VARS; i++) {
    zval_ptr_dtor(&PG(http_globals)[i]);
    /* May be accessed before php_request_startup() */
    ZVAL_UNDEF(&PG(http_globals)[i]);
}

更关键的一手在启动侧：php_request_startup() 里新增 php_basic_early_rinit()，插在 sapi_activate() 之前、请求体解析之前，提前清掉反序列化器等模块的全局状态：

BG(serialize_lock) = 0;
memset(&BG(serialize), 0, sizeof(BG(serialize)));
memset(&BG(unserialize), 0, sizeof(BG(unserialize)));
php_url_scanner_early_rinit();

session 侧还加了 PS(in_rfc1867_update) 标记，上传进度期间的解码强制 incomplete_classes_only 模式——对象一律保持 __PHP_Incomplete_Class，早于业务代码的路径上不再触发 autoload、__wakeup() 等用户代码。

补丁机制概括：退出时机移到安全点，严重故障直接终止进程，跨请求引用在两端都被清理。

看懂补丁的思路，漏洞的形状也就出来了。下面按”公共原语 → 三条路径 → 完整武器化”的顺序拆。

0x03 公共原语：把 fatal 变成可选时的中断

所有路径共用同一个前置能力：精确控制哪一次内存分配触发 fatal。Calif 公开了三个构造方法，都是”请求体字节数 ≠ PHP 内存消耗”的放大器。

绕过 post_max_size 预检。 PHP 拿声明里的 Content-Length 和 post_max_size 比较后就开始收 body；chunked 传输、无长度的 HTTP/1.1、HTTP/2，或者配了输入解压过滤器，都能让”声明小、实读大”。预检查的是声明值，真正喂进来的字节数没有同等的闸门。

空文件条目的元数据放大。 multipart 里 filename="" 的 part 不占 max_file_uploads 名额，但 PHP 照样为它建满 6 个 $_FILES 条目：name / full_path / type / tmp_name / error / size。字段名再套上嵌套：

--BOUNDARY
Content-Disposition: form-data; name="files[a][b][c]...[z]"; filename=""

--BOUNDARY--

每个空文件 part 都要为 6 个条目各建一遍嵌套 HashTable / Bucket / key 字符串。几十 KB 的 body 撑出远超自身的堆分配，几 MB 的请求就能打穿默认 128M 的 memory_limit，而且哪一次分配先爆、什么时候爆，都可以靠调整 part 排布来选。

这就把 Allowed memory size exhausted 从偶发故障变成了攻击者手里的定时器。

0x04 路径①：HashTable 桶的半初始化窗口（CVE-2026-109618）

Calif 的源码审计在 _zend_hash_str_add_or_update_i 里找到第一个中断点。插入新元素的顺序是：

idx = ht->nNumUsed++;
ht->nNumOfElements++;

p = ht->arData + idx;
p->key = zend_string_init(str, len, persistent); /* may zend_error_noreturn() */

p->h = ZSTR_H(p->key) = h;
ZVAL_COPY_VALUE(&p->val, pData);

计数先加，key 分配在后。zend_string_init 触发 OOM bailout 时，桶内容还没写，但 nNumUsed 已经把它划进了”有效”范围。teardown 按计数遍历：

for (p = ht->arData; p != ht->arData + ht->nNumUsed; p++) {
    i_zval_ptr_dtor(&p->val);      /* 把 stale 字节当 zval 析构 */
    if (p->key) {
        zend_string_release(p->key);
    }
}

从清理代码的视角，”有一个元素”成立；从元素自身的视角，它从未完成初始化。半初始化的桶字节被当成 live zval 走析构——UAF 原语到手。

为什么只有 mod_php：这条路径的中断发生在 php_request_startup() 阶段，此时 POST 变量注册（php_register_variable_ex() → zend_symtable_str_update_ind() → 上面那个函数）还没轮到业务代码。两个 SAPI 对启动失败的处理不同：

mod_php:  php_request_startup() 失败 → 请求清理照常执行
          → zend_array_destroy($_POST/$_FILES) 消费坏表 → worker 存活复用

PHP-FPM:  php_request_startup() 失败 → php_module_shutdown() + return
          → worker 直接退出，坏表随进程消失

mod_php 的 sapi_apache2.c 里请求构造失败只是 zend_bailout() 到外层 handler，php_apache_request_dtor() 依旧会调 php_request_shutdown(NULL)。这正是官方在 mod_php 上验证 RCE、而对 109618 的 FPM 只给出”源码分析受影响”的原因。

SAPI 对失败请求的处理分流：mod_php 清理后复用 worker，FPM 启动失败退进程、运行期异常则复用——后者正是路径③的落脚点。

0x05 路径②：session 全局的悬空指针（CVE-2026-109619，PHP ≥ 5.4）

第二类中断点更漂亮：session.upload_progress 这个默认开启的功能，让 multipart 解析在模块初始化完成之前就摸到了 session。

看 main/main.c 的启动顺序：

php_hash_environment();   /* 解析 $_POST/$_FILES —— multipart 在这里 */
zend_activate_modules();  /* 各扩展的 RINIT */
PG(modules_activated) = 1;

multipart 的 FILE_START 事件回调里，upload progress 会调 php_rinit_session(0) 并把 PS(id)、PS(http_session_vars) 写进 session 模块全局——此刻 PG(modules_activated) 还是 0。状态已经发布，但生命周期标记还没立起来。

此后 OOM fatal 发生，请求关闭按 modules_activated 分流：

if (PG(modules_activated)) {
    zend_deactivate_modules();      /* session RSHUTDOWN 被跳过 */
}
shutdown_memory_manager(...);       /* 请求堆照常释放 */

session 的 RSHUTDOWN 没跑，PS(id) / PS(http_session_vars) 还指着已经释放的堆内存，而 mod_php 的 worker 活着接下一个请求。

消费端同样藏在 upload progress 里。请求 B 只要带 PHPSESSID 和 PHP_SESSION_UPLOAD_PROGRESS 字段、不带文件 part，就只走 MULTIPART_EVENT_END 不走 FILE_START——提前重置被绕过，END 回调的 cleanup 重新进入 php_session_initialize()：

请求 A: 文件 part → 提前初始化 session → 状态发布 → OOM fatal
        → 跳过 session RSHUTDOWN → 请求堆释放 → worker 存活

请求 B: 无文件 part → FILE_START 重置被绕过 → END cleanup
        → php_session_track_init() → zval_ptr_dtor(悬空的 PS(http_session_vars))

一次 zval_ptr_dtor 落在攻击者控制的内存上，后续怎么走完全取决于谁先重占了那块堆——这正是后面 9bie 武器化的主战场。这条路径 PHP 5.4 起就存在，全程默认配置，应用侧零配合。

0x06 路径③：反序列化器全局悬空（打 FPM 的钥匙）

FPM 启动失败会退 worker，那就在启动成功之后制造中断。Calif 找到的入口是 PHP 通用反序列化器的共享状态：

if (BG(serialize_lock) || !BG(unserialize).level) {
    d = emalloc(sizeof(struct php_unserialize_data));
    /* 初始化引用表和析构表 */
    if (!BG(serialize_lock)) {
        BG(unserialize).data = d;
        BG(unserialize).level = 1;
    }
} else {
    d = BG(unserialize).data;      /* 复用全局状态 */
    ++BG(unserialize).level;
}

应用执行 unserialize() / session_decode()（WordPress 的 maybe_unserialize() 这类封装也算）期间发生 OOM fatal，php_var_unserialize_destroy() 被跳过：BG(unserialize).data 悬空、level 停在非零。因为这次 fatal 在成功启动之后，FPM 的 worker 正常存活。

下一个 multipart 请求的 upload progress 在 Basic 模块 RINIT 之前进入解码，level != 0 让它把悬空指针当活动状态复用。此时请求 B 的普通字段分配已经把那块内存重占，解码器读到的”引用表 / 析构表”全是攻击者数据。Calif 给出的写原语尤其致命——析构块的 used_slots 是有符号数：

slot = destructor_block + 16 + 16 × used_slots

used_slots 为负时 slot 指向块前任意偏移；序列化数据里的重复 key 触发 var_push_dtor_value()，把一个完整的 zval（指针＋类型）写进选定的位置。受控地址写受控 zval，配合堆布局就是完整的类型混淆原语。mod_php / FPM 通吃，也是官方在 FPM 上验证 session 生命周期 RCE 的机理。

0x07 武器化：9bie 公开利用链逐段拆解

机理有了，从”UAF 原语”到”一条命令出 uid”之间还隔着 ASLR、堆布局和触发稳定性。ASLR（Address Space Layout Randomization，地址空间布局随机化） 是操作系统的一种防护机制：让程序、共享库、堆和栈等区域的装载或分配位置随机化，增加预测内存地址的难度；具体随机化范围取决于平台和构建配置。9bie/php2shell-bypass-aslr-exp 把这最后一公里也公开了：目标 php:8.4.26-apache 官方镜像 + Apache prefork 单 worker，README 报 3/3 成功。以下结合 exploit.py 与 NOTES.md 做静态分析；成功次数为仓库作者报告，本稿未独立运行其 RCE 实验。

区域基址与堆内对象排列属于不同层次；图中位置与宽度均为示意。

Stage 0：worker 轮换——prefork 白送的地址稳定性

A 请求（一堆 3KB 存活字段＋12MB OOM 字段）把 child 打到 SIGABRT，prefork master 立即 fork 新 worker。关键性质：fork 继承父进程的内存映射，同一个 Apache master 之下，新 worker 的 libphp 基址和 Zend MM 2MB chunk 布局与旧 worker 完全一致。

于是 ASLR 只在每个 stage 首次需要对付一次，失败重试也只需 rotate() 换个 worker 重来（master 重启后基址才重新随机）。这个”轮换原语”是整条链的工程地基。

Stage 1：Set-Cookie 堆泄漏——把 zend_string.len 改大

目标：拿到 Zend MM chunk 基址。A 请求按路径②的配方留下悬空 session 状态，额外加两个条件：

  • 1001 个字段触发 max_input_vars 警告。display_errors=On 时警告输出把 headers_sent 置 1，后续 PHP 才有机会在响应里加头；
  • PHPSESSID=\x00 的非法 SID 逼 PHP 生成新 id 并 send_cookie=1——Set-Cookie 就是外带数据的信道。

B 请求用 56 字节的字段值缓冲区重占悬空 reference，再补一个 79B 的”伪造字段”，在第 0x10 偏移写入超大的 zend_string.len：

forge = bytearray(b"A" * 79)
struct.pack_into("<Q", forge, 0x10, 0x1000)   # 伪 zend_string len=4096
forge[0x18] = ord("L")
parts.append({"name": "1999", "data": bytes(forge)})

session 写 cookie 时对（早已被释放、现被攻击者数据占据的）session id 做 php_url_encode()，按伪造的 4096 字节长度一路越界读，把堆里约 4KB 的内容 urlencode 进 Set-Cookie 带出来。

解析端做统计恢复：滑窗取 8 字节小端值，落在用户态指针区间的按 2MB 对齐折叠取众数——chunk 基址就是出现最多的那个值。一堆堆指针自然聚在同一个 2MB chunk 里，统计比精确定位更稳。

Stage 2：libphp 泄漏——HashTable 恰好对齐 pDestructor

光有 chunk 基址不够，还需要 libphp 基址。B 请求构造 983 个数组字段，其中第 406 个组 16 元素 × 16B 值——精心定尺寸的一页 HashTable 分配恰好重占悬空的 PS(id)：

ZSTR_LEN(PS(id)) 读到的是 HashTable 的 nTableSize=16
cookie 数据从 PS(id)+0x18 起 = nNextFreeElement | pDestructor
而 pDestructor = ZVAL_PTR_DTOR，是 libphp 里的固定符号

解析端双重校验：低 12 位必须等于 zval_ptr_dtor 偏移的低 12 位，且解出的基址 4KB 对齐。两次泄漏拼起来 ASLR 全破，全程只用 HTTP 响应头，不碰 libc。

Stage 3：fake 析构链——让 PHP 自己调 zif_system

执行阶段不再泄地址，改为直接覆写悬空 reference。A 请求用 6 组 pad 把 reference 钉到 chunk 内固定偏移；B 请求一个 15B 的 carrier（bin-40 zend_string 的字符区正好落在 reference 头上）只改低 7 字节指针、保留高字节规范零，把 val.value 指向一个 167B 存活字符串里的三件套：

fake HashTable      pDestructor = libphp + zif_system 偏移
fake execute_data   num_args=1, arg1 → 指向命令字符串的 IS_STRING zval
fake zend_string    命令本体（≤14 字节，167 − 0x98 − 1）

触发完全走 PHP 自身的析构路径，无需任何注入：

php_session_track_init()
  → zval_ptr_dtor(PS(http_session_vars))
    → zend_reference_destroy(R0)
      → zend_array_destroy(fake HT)
        → zend_hash_destroy(fake HT)
          → pDestructor(&bucket->val)      # = zif_system(cmd)

zend_hash_destroy 遍历到唯一 bucket 时调 pDestructor(&p->val)——参数地址恰好就是预制的 fake execute_data，zif_system 按标准内部函数从 call frame 取出参数执行命令。不 ROP、不碰栈、不依赖 libc，比 NOTES.md 里早期方案的 pop rdi; ret + popen@plt 干净一个量级。命令上限 14 字节，任意命令用 sh</out/c（8 字节）从挂载目录读脚本绕过。

顺手盘点：研究笔记里的可复用部件

NOTES.md 记录了完整的探索过程，几个部件在别的场景同样好使：

  • stream_bucket_new() 320B 裸喷：给 stream filter 喂 payload，得到内容完全可控、且被资源保活的裸缓冲——早期 Defect D 线（session_unset() + __destruct 写 $_SESSION 触发 zend_hash_clean 重入 → resize 释放旧 arData → 320B 重占 → fake HT）就是靠它拿下的首个 RCE；
  • php_serialize 重入泄漏：__serialize() 里清空 $_SESSION 释放正在序列化的数组，zend_reference 重占 32B 字符串块后 val.type_info 被当 len，一次 775B 越界读带出堆指针；换 4096B 块则伪造 len=32768 读 32KB，固定偏移处捞出 libphp 代码指针。注意默认 php handler 已被 GH-16590 堵住，此路要 php_serialize；
  • A/B 请求对本身就是一个通用模式：A 制造悬空＋内存布局，B 重占＋消费，中间靠 prefork 轮换保证地址连续性。

0x08 防御：在链条上动刀

理解了链条，缓解措施的位置就清楚了：

安装官方修复：升级到官方已发布的修复版本，或安装发行版明确回补这两个 CVE 的包，并重启全部 PHP worker。本次首批修复版本为 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35；实际更新时以官方当前安全公告和发行版维护记录为准。补丁同时调整 OOM 处理、请求结束清理和 early RINIT，分别处理异常退出时机、失效引用和过早访问的问题。

临时缓解按环节选：

  • session.upload_progress.enabled=0 斩断路径②③的消费者——B 请求的提前 session 处理直接消失，官方和 Calif 都点名的首选。这功能默认开启而几乎没人用，关了损失很小；
  • memory_limit=-1 移除 OOM 生产者，但引入资源耗尽风险，只配合容器 / cgroup 边界短期用。RLIMIT_AS / RLIMIT_DATA 反而会制造底层分配失败，官方明确警告别用；
  • 关 display_errors 能掐掉 9bie 当前的泄漏信道（依赖警告输出置 headers_sent），但仓库已声明 off 版在路上，这只争取时间。

检测面（来自利用代码的具体特征）：异常巨大的 Set-Cookie（约 4KB urlencoded 乱码，最强单点信号）；带 PHP_SESSION_UPLOAD_PROGRESS 却无文件 part 的 multipart 请求；单请求上千字段或单字段十几 MB；worker 反复 SIGABRT 的 502 尖峰；日志里 Session ID is too long or contains illegal characters 与 Failed to read session data 成对出现。

三类问题涉及不同状态，补丁分别处理元素可见性、请求内存引用和共享解码上下文。

0x09 小结

PHP2Shell 的价值在于它把一条二十年前埋下的线走通了：内存耗尽从”故障”变成”可控中断”，中断又恰好落在内部状态发布与提交的窗口里。三条路径共享同一个生产者原语，消费端分别击中 HashTable 计数、session 全局和反序列化器全局；SAPI 的启动失败处理差异决定了 mod_php 先倒下，而应用层解码操作让 FPM 同样失守。

补丁的修法也值得回味：把软 OOM 的处理移到受控检查点，用硬限约束继续分配的余量，再补齐请求两端的状态清理。对写 C 的工程师来说，这提醒我们重新审视“先更新记录，再执行可能失败的操作”这种常见顺序：操作中断后，后面的代码究竟会把记录当成什么状态？

IceSolst 在 X 上的这段调侃，倒很贴切：

如果你先发布补丁，它会得到一个 PoC。

如果你不发布补丁，人们会在你身上烧掉数百万个 token，并得到更多 PoC，包含你尚未修补的新漏洞。

这轮修复也值得继续跟踪：同类问题可能仍有遗漏，后续研究还可能找到新的异常路径或变体。 PHP 官方当前将这些版本列为两项已披露漏洞的修复版本；“这类问题是否已经全部找完”，则是另一个需要持续研究的问题。本文尚未验证针对完整官方修复版本的新绕过。先更新，再关注 PHP 官方安全公告、版本更新记录、watchTowr 的 PHP2Shell 跟踪分析 和发行版后续通告，两件事应当一起做。

对维护者来说，修复、回归测试和后续审计需要持续推进；对使用者来说，及时更新并确认运行中的 worker 已切换，仍然是当下最实际的行动。
